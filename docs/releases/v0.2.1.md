# Cloud v0.2.1

Self-hosted file storage with an embedded web interface, CLI and MCP server.

## What's new

- Refresh the web interface with a console-oriented layout, updated settings,
  storage views, mobile navigation and screenshots.
- Fix the phone menu and prevent unwanted form zoom in the installed web app.
- Sync uploaded chunks before acknowledging progress. Reject a missing staged
  prefix and invalid final bodies instead of publishing incomplete content.
- Retain completed upload receipts so a lost final reply or process restart can
  be resolved through HEAD. Retry publication without creating another suffix
  after a failure saving the result in SQLite.
- Recheck quota before publication and recheck refreshed expiry during cleanup.
- Repeat folder uploads safely in the web interface, CLI and MCP: reuse same-name
  files only when every byte matches, and report different content as a conflict.
  Identical retries need temporary disk space but no additional logical quota.
- Publish CLI/MCP downloads under their final names only after receiving and
  syncing the complete file; preserve existing destinations on failure.

## Choose a download

Each archive contains the server, embedded web interface, CLI and MCP server
in one executable, plus the license and these instructions. No separate Go,
Node.js, PHP or database installation is required.

These executables are not code-signed or notarized.

## Start the server

Extract the archive into a writable directory, then run on Linux/macOS:

```sh
./cloud serve
```

On Windows, in PowerShell:

```powershell
.\cloud.exe serve
```

Open `http://localhost:8080` and create your account. The default data directory
is `./data`, relative to the working directory. Keep this directory persistent.
Use `CLOUD_DATA_DIR` to choose a different location and `CLOUD_ADDR` to change
the listening address. Use an HTTPS reverse proxy for remote access.

The same executable also provides `cloud cli help` and `cloud mcp --help`.
On Windows, CLI sessions are encrypted for the current Windows account;
on Linux/macOS, session files require private Unix permissions (`0600`).

## Upgrading from v0.2.0

Stop the service, back up the database and storage together, then replace the
executable and start it with the same configuration. New SQLite migrations retain
existing uploads and add completion receipts and folder conflict policy. Run one
server process against a database and volume. To roll back, stop v0.2.1 and restore
both the database and storage backup before starting the previous executable.

Staging and published files must share a filesystem supporting hard links.
CLI/MCP download destinations also require hard-link support. A killed download
can leave a `.cloud-download-*.part` temporary file; its final name is not published
until the transfer completes. Filesystem corruption and sudden power loss remain
outside the process-restart guarantees.

Repeating a directory upload retransmits files for comparison; it does not resume
an entire directory from a persistent manifest. Unfinished sessions keep quota
reservations until resumed, terminated or expired. Individual CLI resume requires
the same unchanged source file.

See [transfer behavior](https://github.com/din9xtr/cloud-control-panel/blob/v0.2.1/docs/transfers.md),
[connection setup](https://github.com/din9xtr/cloud-control-panel/blob/v0.2.1/docs/clients.md),
[CLI](https://github.com/din9xtr/cloud-control-panel/blob/v0.2.1/docs/cli.md)
